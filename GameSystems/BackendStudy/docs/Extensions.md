# 확장 설계 — 여기서 더 나아간다면

> 1~5단계로 멀티플레이 백엔드의 핵심은 완성됐다. 이 문서는 **구현하지는 않았지만, 어떻게 확장할지 설계까지 정리**한 항목들이다.
> 각 항목은 **왜 필요한가 → 어떻게 접근하나 → 지금 코드 어디가 바뀌나 → 트레이드오프** 순서로 설명한다.
> ([← 전체 로드맵으로 돌아가기](../README.md))

---

## 1. 자동 재연결 (Auto Reconnect)

### 왜 필요한가
지금은 연결이 한 번 끊기면(와이파이 끊김, 서버 재시작 등) **영영 다시 붙지 않는다.** 1단계에서 "재연결 없음"을 한계로 남겨뒀던 그 부분이다. 실제 게임에서는 네트워크가 잠깐 끊기는 일이 흔하고, 그때마다 게임을 껐다 켜게 하면 안 된다. 그래서 클라가 **끊김을 감지하면 스스로 다시 접속을 시도**해야 한다.

이건 서버가 아니라 **클라이언트가 담당하는 기능**이다. 게임 클라이언트 개발자가 실제로 자주 만드는 부분이다.

### 어떻게 접근하나
큰 흐름은 세 단계다.

1. **끊김 감지:** 클라의 읽기 루프(`ReadLoop`)에서 `Read`가 0을 반환하거나 예외가 나면 "끊겼다"고 판단한다. (이미 1단계에서 이 감지는 하고 있다 — 로그만 찍고 끝냈을 뿐.)
2. **재접속 시도:** 끊김을 감지하면 곧바로 `Connect()`를 다시 부른다. 실패하면 잠깐 기다렸다 또 시도한다. 이때 **매번 즉시 재시도하지 않고 간격을 두는 것**이 중요하다(예: 1초 → 2초 → 4초로 점점 늘림). 서버가 잠깐 죽었을 때 수천 번씩 두드리면 서버에 부담이 되기 때문. 이걸 "백오프(backoff)"라고 한다.
3. **상태 복원:** 재접속에 성공하면 그냥 붙은 게 아니라, **다시 로그인하고 이전 상태로 돌아가야** 한다. 3단계 로그인 → 4단계 위치 복원 → 5단계 GameWorld 재입장이 자동으로 이어져야 한다.

### 지금 코드 어디가 바뀌나
- **`NetworkManager` (클라):** 끊김 감지 시 재접속 루프를 도는 로직 추가. "지금 재접속 시도 중"인지 상태를 관리해야 한다.
- **로그인 정보 임시 보관:** 재접속 후 자동 로그인하려면, 클라가 아이디를 기억해뒀다가 다시 보내야 한다. (비밀번호를 계속 들고 있는 건 보안상 좋지 않아, 실무는 재접속용 토큰을 쓰기도 한다.)
- **서버 쪽은 거의 안 바뀐다** — 서버 입장에선 "새 연결이 하나 들어와 로그인하는 것"과 똑같기 때문. (다만 5단계에서 본 "같은 계정 중복 로그인" 처리와 엮인다 — 끊긴 옛 세션을 정리해야 새 세션이 깔끔히 들어온다.)

### 트레이드오프
- **재시도 간격:** 너무 짧으면 서버에 부담, 너무 길면 사용자가 오래 기다린다. 백오프로 균형을 잡는다.
- **상태 복원의 복잡도:** "어디까지 복원할 것인가"를 정해야 한다. 위치만? 진행 중이던 전투까지? 복원 범위가 넓을수록 구현이 복잡해진다.
- **끊김과 정상 종료 구분:** 사용자가 일부러 나간 건지, 네트워크가 끊긴 건지 구분해야 한다. 일부러 나갔는데 자동 재접속하면 안 되니까.

## 2. 전송 암호화 (TLS)

### 왜 필요한가
지금 통신은 **평문**이다. 즉 클라와 서버 사이를 오가는 데이터(로그인 아이디·비밀번호 포함)를 누군가 중간에서 훔쳐보면 그대로 읽힌다. 3단계에서 비밀번호를 해싱해 저장했지만, **로그인할 때 비밀번호가 네트워크를 지나가는 그 순간**은 평문이라 도청에 노출된다. 3·5단계에서 "지금은 평문이라 취약하다"고 계속 짚었던 부분이 이것이다.

정리하면 보안은 세 층이다: 저장 보안(해싱, 3단계) + 신원 보안(세션, 3단계) + **전송 보안(암호화, 여기)**. 앞의 둘은 했고, 이걸 하면 보안 이야기가 완결된다.

### 어떻게 접근하나
직접 암호화 알고리즘을 짜지 않는다. .NET이 제공하는 **`SslStream`**으로 기존 통신을 감싸면 된다. 지금 우리는 `NetworkStream`(맨 데이터)으로 읽고 쓰는데, 그걸 `SslStream`으로 한 겹 감싸면 **그 안을 지나는 모든 데이터가 자동으로 암호화**된다. 중간에서 훔쳐봐도 암호문이라 못 읽는다.

- 서버는 "인증서"를 하나 갖고, 연결이 맺어질 때 이 인증서로 암호화된 통로를 연다.
- 클라는 그 통로에 붙어서 통신한다.
- 개발/학습 단계에서는 직접 만든 자체 인증서(self-signed)를 쓰고, 실서비스는 신뢰된 기관이 발급한 인증서를 쓴다.

### 지금 코드 어디가 바뀌나
- **`PacketFraming` (서버·클라):** 지금 `NetworkStream`을 대상으로 읽고 쓰는데, 그 대상을 `SslStream`으로 바꾼다. **프레이밍 로직 자체(길이 헤더 + 본문)는 그대로** — 그 아래 통로만 암호화되는 것이라, 우리가 짠 코드는 거의 안 바뀐다. 이게 핵심이다: 암호화는 "통로"의 문제라 "무엇을 보내는가"는 그대로다.
- **연결 맺는 부분:** 서버는 연결 수락 후 인증서로 SSL 핸드셰이크를 하고, 클라는 접속 후 SSL 인증 과정을 거친다.

### 트레이드오프
- **CPU 비용:** 암호화·복호화에 연산이 든다. 다만 현대 하드웨어에선 대부분 무시할 만하다.
- **인증서 관리:** 인증서를 만들고, 갱신하고, 안전하게 보관해야 하는 운영 부담이 생긴다.
- **디버깅 난이도:** 통신이 암호화되면 중간에서 패킷을 눈으로 확인하기 어려워진다(개발 중엔 불편할 수 있다).

## 3. 서버 로그 (구조화된 로깅)

### 왜 필요한가
지금은 서버가 `Console.WriteLine`으로 로그를 찍는다. 개발 중엔 충분하지만, 실제 운영에선 문제가 있다: 서버를 끄면 로그가 사라지고, 로그가 많아지면 콘솔에서 찾기 어렵고(5단계에서 PositionUpdate 도배를 겪었다), "언제 무슨 일이 있었나"를 나중에 추적할 수 없다.

그래서 로그를 **파일로 남기고, 수준(레벨)을 나누고, 나중에 검색할 수 있게** 만드는 것이 서버 로그다.

### 어떻게 접근하나
1. **로그 레벨 도입:** 로그를 Debug(상세)/Info(일반)/Warning(주의)/Error(오류)로 나눈다. 평소엔 Info 이상만 보고, 문제가 생기면 Debug까지 켠다. (5단계에서 PositionUpdate를 로그에서 뺀 것이 이 개념의 축소판 — 고빈도 로그는 Debug 레벨로 두면 평소엔 숨는다.)
2. **파일 출력:** 콘솔뿐 아니라 파일에도 남겨서, 서버를 꺼도 기록이 유지되게 한다. 날짜별로 파일을 나누면 찾기 쉽다.
3. **로깅 라이브러리 사용:** 직접 짜기보다 `Serilog`, `NLog` 같은 검증된 라이브러리를 쓴다. 레벨·파일 분리·형식을 다 처리해준다.

### 지금 코드 어디가 바뀌나
- **모든 `Console.WriteLine` → 로거 호출로 교체.** 예: `Console.WriteLine("[DB] 연결 성공")` → `logger.Info("DB 연결 성공")`.
- 로거를 한 곳에서 설정(파일 경로, 레벨, 형식)하고, 각 클래스가 그걸 가져다 쓴다.
- **동작 로직은 안 바뀐다** — "무엇을 기록하는가"는 그대로고, "어떻게 기록하는가"만 바뀐다.

### 트레이드오프
- **클라 개발자에겐 상대적으로 덜 중요:** 이건 서버 운영 영역이라, 게임 클라이언트 개발자가 직접 만들 일은 적다. 다만 "서버가 어떻게 문제를 기록하고 추적하는지" 이해하면, 클라에서 버그를 서버 팀과 함께 추적할 때 도움이 된다.
- **성능:** 파일에 쓰는 건 콘솔보다 느릴 수 있어, 고빈도 로그는 모아서 쓰거나(버퍼링) 레벨을 조절한다.

## 4. 매치메이킹 (방 만들기 / 찾기)

### 왜 필요한가
지금은 접속한 모두가 **하나의 공간(GameWorld)**에 다 들어간다. 그런데 실제 게임은 보통 "방"이나 "매치" 단위로 나뉜다 — A와 B는 1번 방에서, C와 D는 2번 방에서 각자 플레이한다. "방 만들기 / 방 목록 보기 / 방 입장"이 매치메이킹이다.

게임 클라이언트 개발자에게 이건 **로비 UI**로 자주 만나는 기능이다(방 목록 화면, 방 만들기 버튼 등).

### 어떻게 접근하나
핵심은 지금의 **하나의 GameWorld를 여러 개로 나누는 것**이다.

1. **방(Room) 개념 도입:** 지금 GameWorld가 "전체 하나"인데, 이걸 "방마다 하나씩" 여러 개 두거나, GameWorld 안에 "방 목록"을 두고 각 방이 자기 플레이어들을 관리하게 한다.
2. **방 관련 패킷 추가:** `CreateRoom`(방 생성), `RoomList`(방 목록 요청), `JoinRoom`(방 입장) 등.
3. **전파 범위 변경:** 지금은 위치·채팅을 "전체"에게 전파하는데, 이걸 **"같은 방 사람에게만"** 으로 바꾼다. 1번 방의 움직임이 2번 방에 보이면 안 되니까. (5단계에서 "관심 영역(AoI)"으로 언급한 개념과 이어진다 — 방은 가장 단순한 형태의 관심 영역이다.)

### 지금 코드 어디가 바뀌나
- **`GameWorld`:** "전체 플레이어 하나의 목록"에서 "방별 플레이어 목록"으로 구조가 바뀐다. 가장 큰 변경.
- **`PacketHandler`:** 방 생성·입장·목록 패킷 처리 추가. 로그인 후 바로 GameWorld 입장이 아니라, "로그인 → 로비 → 방 선택 → 입장"으로 흐름이 바뀐다.
- **전파 로직:** `BroadcastExcept`, `TickBroadcastAsync`, 채팅 전파가 모두 "같은 방 안에서만"으로 범위가 좁아진다.
- **클라:** 로비 UI(방 목록, 방 만들기, 입장 버튼)가 새로 필요하다.

### 트레이드오프
- **규모가 크다:** 매치메이킹은 그 자체로 5단계만큼의 작업이다. "빈 방 정리, 방 최대 인원, 방장 위임, 방 중간 입장/퇴장" 등 처리할 게 많다.
- **복잡도 vs 필요성:** 게임 종류에 따라 방식이 크게 다르다(방 기반 vs 자동 매칭 vs 오픈월드). 만들려는 게임이 정해지면 그에 맞춰 설계해야 해서, "일반적인 매치메이킹"을 미리 다 만들긴 어렵다.
- **인디 현실:** 앞서 다룬 것처럼, 인디는 이 로비/매칭을 직접 안 만들고 스팀 같은 플랫폼의 매치메이킹·릴레이 기능을 빌려 쓰는 경우가 많다.

## 우선순위 정리 (게임 클라이언트 개발자 관점)

| 확장 | 클라 개발자에게 | 규모 | 비고 |
|---|---|---|---|
| 자동 재연결 | ⭐ 매우 유용 (순수 클라 로직) | 중 | 실전에서 자주 만듦, 1단계 숙제 회수 |
| 전송 암호화 | 이해 차원에서 유용 | 소~중 | 보안 완성, 보통 프레임워크가 처리 |
| 매치메이킹 | 유용 (로비 UI) | 대 | 그 자체로 큰 프로젝트, 게임 종류별로 다름 |
| 서버 로그 | 간접적 (서버 영역) | 소 | 클라와 직접 관련은 적음 |

**만약 하나를 실제로 구현한다면 "자동 재연결"이 클라 개발자 포지션에 가장 잘 맞는다.** 순수하게 클라이언트가 담당하는 기능이고, 재접속 후 로그인·위치 복원·재입장이 3·4·5단계를 다시 관통하기 때문에, "클라에서 서버 연결을 어떻게 다룰지"를 종합적으로 이해하게 된다.
